    Encrypting a node's state in place: the journal and the order of writes

    Status: the engine is built (T-1136, crates/kithd/src/in_place.rs, tested on files with every cut); nothing calls it yet. Its wiring into init is T-1137, the real dm-crypt mapper is the slice after. This record is the part of T-1106 that the cuts depend on. Where the code differs from a line here, the code is the word. It builds on adr-unlock.md (the lock record, at 512 KiB into the config partition) and on the order of writes of adr-second-disk.md.

    The problem #

    A node installed without encrypt: true has its state plain on the state partition. To encrypt it with no reinstall, every byte of the partition is read and written back through a dm-crypt mapping of the same partition. That takes minutes to hours, and the power can go at any byte of it. Whatever the moment, the partition must still be readable on the next start: every chunk either plain, or encrypted with the journal saying where the line is. A chunk half plain and half encrypted with no way to say which is the failure this record exists to make impossible.

    What the engine is #

    A pure pass: no init, no CLI, no dm-crypt call. It is given three things that are all "read, write and sync at an offset" (the Disk trait; a file in the tests):

    • the partition, raw, where the plain data is read from;
    • the mapping, the same partition under the key: a write to it lands encrypted on the partition (a fake that XORs in the tests, kith_dm_sys::crypt in the slice that wires it);
    • the journal, in the config partition, which is not under the key.

    It goes through the partition in chunks of 256 KiB (the last one is what is left), in order. The size of the partition and of the chunk are in the journal and checked at every resume: a partition that grew or shrank is refused, not guessed at.

    1. The layout of the journal #

    The config partition is 1 MiB. Its first 64 KiB is the node's config; the lock record is 4 KiB at 512 KiB with a copy after it (crypt::AT). The journal sits between them:

      0 KiB      64 KiB            128 KiB  132 KiB  136 KiB      192 KiB            452 KiB      512 KiB   520 KiB      1 MiB
  | config   | (free)          | head 1 | head 2 | (free)      | backup slot      | (free)     | lock    | lock copy  | (free)
    • two header copies, 4 KiB each, at 128 KiB and 132 KiB: a magic line, the pass's random id, the partition's size, the chunk size, done (chunks whole at rest) and the SHA-256 of all of that; the rest of the 4 KiB is zero. A header that fails its sum, or has a byte after it, is not taken;
    • one backup slot at 192 KiB, 256 KiB plus 4 KiB: a random 12-byte nonce, then the plain chunk sealed (ChaCha20-Poly1305) under a key drawn from the state's key with HKDF, with the pass id and the chunk's number as the associated data. The slot is never plain, so nothing plain is left outside the partition. A slot from another pass, or of another chunk, does not open.

    The test in_place::layout holds these ranges apart from each other, from the node's config and from the lock record, and inside 1 MiB.

    2. The order of writes #

    At the start (no whole header, the second copy empty): write header 1 with done = 0, sync, write header 2, sync. Nothing of the partition is touched before both are down.

    For each chunk i, with done = i:

    1. read the plain chunk from the partition;
    2. seal it into the backup slot, sync;
    3. write it through the mapping, the first half and then the second, sync;
    4. write done = i + 1 to header 1, sync, then to header 2, sync.

    At the end: zero the backup slot, sync. The journal is left saying "all done"; the caller clears it (clear) once the mapping is the node's state.

    Two rules carry everything: the backup of chunk i + 1 is not written until both headers say i + 1, and the partition's chunk i is not written until its backup is on the disk. The syncs between the two header copies are there on purpose: with one sync after both, a disk may keep half of each, and both copies are then torn (the sum catches one torn copy, so one must stay whole).

    3. The cut, at every point #

    A resume reads both headers, takes the whole one with the greater done (both whole: the greater; one: that one; neither: see below), writes both again, then looks in the slot for the backup of chunk done. If it opens, the chunk is written again through the mapping from it, whatever state the chunk is in (plain, half, whole: the mapping gives one ciphertext for one plain chunk and one place), and the pass goes on. If it does not open, chunk done was never touched and the pass reads it from the partition as at any chunk.

    Neither header whole. If header 2 is all zero the pass never got past its first write (header 1 may be torn): it starts. If header 2 holds anything else, the journal is damaged, and the engine stops rather than start again over a partition half encrypted. A header that is whole but says another size or chunk is refused the same way.

    A cut in a resume is a cut like any other: the resume uses the same writes in the same order. The test cuts a second time at every point of the resume and runs a third.

    What a disk may do that a file does not. The tests keep a fake whose writes wait until a sync, and at a cut keep none of them, all of them, the first half of each, or the first 64 bytes of each (a header with its new count and its old sum): so a missing sync shows as a failure and not as a pass on a file that wrote everything at once. (With the sync between the two header copies taken out, the last of these ends in "both copies damaged": the test was run so.)

    What it does not do #

    • It does not read a chunk twice from the raw partition after the mapping wrote it: a raw read of a partition the mapping wrote may come from a page cache that never saw the write. The caller that verifies does so through the mapping, after dropping the cache.
    • A chunk half written whose backup is gone (the slot's own sector failing) is lost; the pass stops rather than seal what is on the partition.
    • No online pass: the partition is not mounted while it runs. No decrypt.
    • The sealed backup is under the state's key, so it is as strong as the state, and no stronger. A lock record that is erased does not erase a backup left in the journal; the engine zeroes the slot at the end and clear zeroes everything.
